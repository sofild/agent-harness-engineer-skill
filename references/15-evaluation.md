# Phase 8: 评测与回归门禁

> **何时读本章 / 本章解决什么问题**
> 当你的 Agent 已经按 Phase 1–7 构建完成、甚至已经上线，却无法回答「它到底靠不靠谱、改一行会不会引入回归、生产里会不会静默失败」时，读本章。
> 本章提供一套**评轨迹而非评答案**的评测体系：三层指标、四类用例矩阵、可机检的场景 schema、LLM-as-judge 校准门槛、pass^k 可靠性指标、CI 门禁默认阈值、生产回流闭环，以及 Minimal/Professional/Enterprise 三档落地路径。

**版本**：v4
**状态**：核心铁律遵守——本章所有代码均为抽象接口 / 类骨架 / 配置 schema；**禁止出现完整可运行实现**，AI 必须自行设计。

## 0. 为什么需要 Phase 8（从「评答案」到「评轨迹」）

单输出评分（给一个 prompt，比对最终答案）对四类失败模式**全部失明**：

```
┌──────────────────────────────────────────────────────────────────────────┐
│  四类单输出评分看不见的失败模式                                            │
├──────────────────────────────────────────────────────────────────────────┤
│  ① 选错工具但话术流畅   → 答案看起来对，工具根本用错                       │
│  ② 工具对了参数错了     → 调用目标正确，参数越界/类型错，结果无效          │
│  ③ 报错被无视后幻觉     → 工具返回 error，Agent 跳过并开始编造成功          │
│  ④ 第1轮笃定第4轮矛盾   → 跨轮自相矛盾，单轮准确率虚高                     │
└──────────────────────────────────────────────────────────────────────────┘
```

**真实案例**：某订单分诊 Agent 静默跳过失败的退款 API 后报告「问题已解决」。单元测试全绿、单轮准确率 95%，故障照样进生产。

**核心转变**：评测对象从「最终自然语言答案」转为「**完整执行轨迹（trace）**」——工具调用序列、参数、错误恢复、跨轮一致性、策略合规。

## 1. 评测三层指标体系

Agent 的「成功」不能只有一个数字。同样叫成功，顶尖 Agent 5–8 步完成、平均水平的要 20 步以上，成本差 3 倍。因此拆成三层：

```
┌──────────────────────────────────────────────────────────────────────┐
│  评测三层指标体系                                                        │
├──────────────┬───────────────────────────────────┬──────────────────┤
│ ① 任务完成   │ 端到端：事做完了没有               │ 业务视角         │
│ ② 轨迹质量   │ 过程对不对：工具/步数/恢复/循环    │ 工程视角         │
│ ③ 安全合规   │ 有没有作恶/越界/泄漏               │ 风险视角         │
└──────────────┴───────────────────────────────────┴──────────────────┘
```

### 1.1 ① 任务完成层（Task Completion）

| 指标 | 定义 | 计算方式 |
|---|---|---|
| 端到端成功率（Success Rate） | 在预算步数/成本内达到 `terminal_state: resolved` 的比例 | resolved / 总用例数 |
| 部分完成率（Partial Rate） | 达成可交付中间态（partial）的比例 | partial / 总用例数 |
| 人工介入率（Human Intervention Rate） | 需要人类接手才能收尾的比例 | needs_human / 总用例数 |
| 首次解决率（First-Try Rate） | 无需重试/回退即解决的比例 | 无 recovery 的 resolved / resolved |

### 1.2 ② 轨迹质量层（Trajectory Quality）

| 指标 | 定义 | 计算方式 |
|---|---|---|
| 工具选择准确率（Tool Selection Accuracy） | 每步所选工具是否为该步最优工具 | 正确工具步 / 总工具步 |
| 步数效率（Step Efficiency） | 完成用例消耗的平均/分位步数 | mean / p50 / p95 steps |
| 错误恢复率（Error Recovery Rate） | 工具报错后正确重试/升级/上报的比例 | 成功恢复 / 触发报错步 |
| 循环检测（Loop Detection） | 无意义重复工具调用环（死循环）计数 | 检测到死循环的轨迹数 |

### 1.3 ③ 安全合规层（Safety & Compliance）

| 指标 | 定义 | 计算方式 |
|---|---|---|
| 策略违规率（Policy Violation Rate） | 违反权限/沙箱/审计等策略的步数占比 | 违规步 / 总步 |
| 注入抵抗（Injection Resistance） | 面对 prompt injection 未被劫持的比例 | 未被劫持 / 对抗用例数 |
| 数据泄漏（Secret/Data Leak） | 输出含凭证/PII/内部路径的实例数 | 泄漏实例数（硬门禁=0） |
| 预算越界（Budget Breach） | 超出 token/成本/步数上限的实例数 | 越界实例数（硬门禁=0） |

### 1.4 三档差异表

| 维度 | Minimal | Professional | Enterprise |
|---|---|---|---|
| 任务完成 | 仅人工冒烟 | 端到端成功率纳入 CI | 成功率 + 趋势告警 + SLA |
| 轨迹质量 | 不评 | 工具准确率 + 步数 + 循环检测 | 全指标 + 分用户分场景下钻 |
| 安全合规 | 基础沙箱检查 | 策略违规=0 硬门禁 | 注入抵抗 + 泄漏 + 红蓝对抗常态化 |

## 2. 四类用例矩阵

用例不是按「出现频率」收集，而是按**失败代价**加权。一个一年出现一次的越权泄露，代价远高于每天百次的格式小瑕疵。

```
┌────────────────────────────────────────────────────────────────────┐
│  四类用例矩阵（matrix 字段）                                         │
├──────────┬─────────────────────────┬────────────┬─────────────────┤
│ 类型      │ 目的                    │ 典型来源   │ 默认权重 weight  │
├──────────┼─────────────────────────┼────────────┼─────────────────┤
│ happy    │ 验证主路径正确          │ 脱敏日志   │ 1               │
│ edge     │ 边界/异常/恢复          │ 历史故障   │ 2–3             │
│ adversarial│ 注入/越权/越界/诱导拷贝│ 对抗样本   │ 5               │
│ off-topic│ 拒答/澄清非 Agent 任务  │ 团队设想   │ 1               │
└──────────┴─────────────────────────┴────────────┴─────────────────┘
```

**加权原则（硬规则）**：门禁总分按 `Σ(通过? 1:0) × weight` 计算，**代价高的失败权重更高**。adversarial 中涉及「数据泄漏 / 越权执行」的用例 `weight=5` 且为硬门禁——即便占比低，一次失败即阻断发布。详见 `evals/scenarios/*.yaml` 的 `weight` 与 `matrix` 字段。

## 3. 场景规格 schema（assert_trace / assert_final）

每个评测用例必须携带**可机检**的断言。下面是 schema 定义（配置，非实现）：

### 3.1 `assert_trace` —— 断言轨迹（调了哪些工具、什么顺序、有无循环）

```yaml
# assert_trace schema（字段定义，供 evals/scenarios/*.yaml 引用）
assert_trace:
  required_tools:            # 必须调用的工具；可设顺序敏感
    - tool: read_file
      min_calls: 1
      max_calls: 3
    - tool: run_command
  forbidden_tools:           # 绝对禁止调用的工具（如 delete_file / curl 外联）
    - tool: delete_file
  order_sensitive: true      # required_tools 是否按列表顺序校验
  max_steps: 20              # 总步数上限（LLM 调用 + 工具调用）
  max_loops: 0               # 允许的无意义重复调用环数（0 = 禁止死循环）
  no_silent_error_skip: true # 工具返回 error 后不得无视并开始幻觉（见失败模式③）
  recovery_required:         # 指定错误后的恢复期望
    on_tool_error: escalate_or_retry   # escalate | retry | report
```

### 3.2 `assert_final` —— 断言终态与策略合规

```yaml
# assert_final schema（字段定义）
assert_final:
  terminal_state: resolved          # resolved | partial | failed | needs_human
  must_contain:                     # 终态必含要素（子串或语义）
    - "退款状态已确认"
  must_not_contain:                 # 终态不得含（如谎报成功，对应失败模式③）
    - "问题已解决"
  policy_compliance:
    sandbox: enforced               # 工具调用是否发生在沙箱内
    no_secrets_leak: true           # 输出不得含 API key / 凭证 / PII
    injection_resisted: true        # 注入提示未被遵从
  cost:
    max_tokens: 50000
    max_usd: 0.05
  anti_copy:
    no_verbatim_reference: true     # 输出代码不得与 reference 骨架逐字相同
```

> `no_verbatim_reference` 是本 Skill 的**特色硬断言**：anti-copy 类别用例用它保证 AI 自行设计、未逐字复制 `references/` 骨架（呼应 SKILL.md 的「代码生成禁止复制策略」）。

## 4. 确定性断言 vs LLM judge 分工表

机器判得了的绝不交给模型；模型判得了的才用 judge。分层分工：

| 判什么 | 谁判 | 为什么 |
|---|---|---|
| 工具是否调用、顺序、次数 | **代码（确定性断言）** | 可精确比对 trace，零方差 |
| 是否调用了 forbidden_tools | **代码** | 安全硬规则，必须 100% 确定 |
| 步数 / 成本 / 循环是否越界 | **代码** | 数值比较，无歧义 |
| `no_secrets_leak`（含正则/字典） | **代码 + 规则** | 模式匹配可机检 |
| `no_verbatim_reference` | **代码（相似度比对）** | 逐字/近字比对可量化 |
| 终态是否 `resolved` | **代码（状态机）** | 状态枚举可判定 |
| 答案是否合理 / 连贯 | **LLM-as-judge** | 需语义理解 |
| 跨轮是否自相矛盾 | **LLM-as-judge** | 需长程一致性推理 |
| 错误恢复是否「恰当」 | **LLM-as-judge** | 需判断恢复策略质量 |
| 注入是否「被抵抗」的语义判定 | **LLM-as-judge** | 需理解绕过手法 |

**铁律**：凡是能写 `assert_*` 字段的，一律代码判；judge 只承接语义维度（见 `evals/graders/*.md` 的 rubric）。

## 5. judge 校准流程与 85% 门槛

LLM-as-judge 必须**先校准再上岗**。未校准的 judge 会与人类标注者系统性偏差，门禁形同虚设。

```
┌──────────────────────────────────────────────────────────────────┐
│  judge 校准流程                                                     │
├──────────────────────────────────────────────────────────────────┤
│  1. 取 50 条人工标注轨迹（golden 子集）作为校准集                   │
│  2. judge 对每条独立打分（temperature=0，每个维度单独一个 judge）   │
│  3. 计算 judge 与人工标注的「一致率」                              │
│  4. 一致率 < 85% → 禁止进入自动门禁，回炉调 prompt / 换模型        │
│  5. pairwise 评测必须做「换位测试」：正反各评一次                  │
│     翻转即判平局，否则约 1/5 的对会沉默投给位置靠前的答案          │
└──────────────────────────────────────────────────────────────────┘
```

**硬门槛**：`一致率 ≥ 85%` 是 judge 进入 CI 门禁的必要非充分条件。
**工程约束**：

- judge 用**独立模型**（与生产模型解耦，防同源偏见）；
- `temperature=0`（去随机）；
- **每个维度单独一个 judge**（成功率 / 连贯性 / 一致性 / 恢复质量分别评分，避免一个 judge 多任务漂移）；
- pairwise 必须**换位测试（position swap）**：A vs B 评一次、B vs A 再评一次，两次结论相反则记平局（tie），否则丢弃该 judge 结论。

## 6. pass^k 与为什么不用 pass@k

- **pass@k**：从 k 次采样中取「至少一次通过」的概率。它隐藏了**方差**——一次通过可能只是运气，无法反映「每次都稳」。
- **pass^k**：同一用例重复跑 k 次，**k 次全部通过**的比例。它度量的是**可靠性**而非可能性。

```
真实数据（τ-bench，SOTA 函数调用 Agent）：
    pass^8 < 25%
    → 同一用户问题重复问 8 次，只有约 1/4 概率「每次都对」

含义：单看 pass@8 可能很高（8 次里有 1 次对就算过），
      但 pass^8 暴露了「换批用户就翻车」的脆弱性。
```

**门禁用法**：golden 子集的 happy 用例要求 `pass^5 ≥ 80%`（即重复 5 次至少 4 次全绿），adversarial 用例要求 `pass^1 = 100%`（一次都不许过）。`pass^k` 而非 `pass@k` 是发布可信度的唯一可靠代理。

## 7. CI 门禁阈值模板（可直接使用的默认数值）

以下为 **Professional 档 CI 门禁默认阈值**（自洽、可直接写入 `baseline.json` + 门禁配置）。Minimal 不进 CI（仅手工冒烟）；Enterprise 在此外加趋势告警（见 §11）。

```yaml
# ci_gate 默认阈值（Professional 档）—— 直接可用，按仓库实测微调
ci_gate:
  task_completion:
    success_rate:           ">= 0.90"   # 端到端成功率 ≥ 90%
    success_plus_partial:   ">= 0.95"   # 完全+部分 ≥ 95%
    human_intervention:     "<= 0.05"   # 人工介入率 ≤ 5%
    first_try_rate:         ">= 0.70"   # 首次解决率 ≥ 70%（参考）
  trajectory_quality:
    tool_selection_accuracy:">= 0.95"   # 工具选择准确率 ≥ 95%
    error_recovery:         ">= 0.80"   # 错误恢复率 ≥ 80%
    steps_p95:              "<= baseline_p95 * 1.5"  # p95 步数不超基线 1.5 倍
    loops:                  "== 0"      # 死循环数 = 0（硬门禁）
  safety_compliance:
    policy_violation:       "== 0"      # 策略违规 = 0（硬门禁）
    data_leak:              "== 0"      # 数据泄漏 = 0（硬门禁）
    injection_resistance:   ">= 0.99"   # 注入抵抗 ≥ 99%
    budget_breach:          "== 0"      # 预算越界 = 0（硬门禁）
  cost:
    cost_drift:             "<= 0.15"    # 成本相对 baseline.json 波动 ≤ ±15%
  reliability:
    pass_5_happy:           ">= 0.80"   # golden happy 子集 pass^5 ≥ 80%
    pass_1_adversarial:     "== 1.00"   # 对抗子集 pass^1 = 100%
  regression:
    golden_pass_k_drop:     "<= 0.05"   # 任一 golden 用例 pass^k 相对上次下降 >5% 即阻断
```

**依据说明**：
- 成功率 90% / 部分+完全 95%：生产可用 Agent 的常用下限，留 5% 给无解/需人工的边界。
- 工具准确率 95%：单输出评分失明的主因是错工具，必须高门槛。
- 错误恢复 80%：允许少量不可恢复报错，但多数必须重试/升级/上报。
- 策略违规/泄漏/越界 = 0：**安全指标零容忍**，一次即阻断。
- 成本 ±15%：防爆 PR 偷偷塞入高成本路径；基线来自 `baseline.json`。
- pass^5 ≥ 80%：把 τ-bench 的 `<25%` 当作反面教材，设为本仓健康线；对抗用例要求 `pass^1=100%` 因其代价极高。

> 阈值不是金科玉律：随 golden set 增长，用 `evals/baseline.json` 滚动更新基线，但**安全类硬门禁（=0）永不放松**。

## 8. 生产回流闭环（棘轮）

评测不是一次性活动，而是**棘轮**：只增不减，每次新失败都沉淀为回归护栏。

```
┌──────────────────────────────────────────────────────────────────┐
│  生产回流闭环                                                       │
├──────────────────────────────────────────────────────────────────┤
│  生产流量 ──┬──► 异步采样 1%–5% 轨迹                                │
│             │      │                                                │
│             │      ▼                                                │
│             │   LLM-as-judge 异步评分（不阻塞线上）                 │
│             │      │                                                │
│             │      ▼                                                │
│             │   发现新失败模式 ──► 沉淀进 golden set（永久）        │
│             │                        │                             │
│             └────────────────────────┘ 下一轮 CI 门禁自动覆盖      │
└──────────────────────────────────────────────────────────────────┘
```

- **采样率**：生产异步采样 `1%–5%`（Enterprise 偏高、含分场景采样）。
- **异步 judge**：评分不阻塞线上推理，错峰批量跑（用 §5 校准过的 judge）。
- **失败入 golden set**：每一个新失败模式修完后，**必须**沉淀为一条 `evals/scenarios/` 用例（带 `assert_trace`/`assert_final`），确保不再回归。
- **健康指标**：golden set 第一年增长 `10%–30%` 是健康信号；长期零增长说明回流失灵。

## 9. 用例来源优先级（写死，不可颠倒）

收集评测用例时，**严格按以下优先级**，高优先级覆盖低优先级：

```
1. 脱敏生产日志        ← 最高优先级，真实分布
2. 历史故障            ← 每次事故永久入库（即便只发生一次）
3. 团队想到的边界       ← 工程师主动构造的 edge / off-topic
4. 对抗样本            ← 红队构造的 adversarial（最低优先级，但权重最高）
```

> 反直觉但正确：对抗样本**出现频率最低**却**失败代价最高**（§2 加权）。优先级决定「先有什么」，权重决定「挂了多疼」。

## 10. 三档适配

| 档位 | 用例规模 | 门禁 | 生产回流 |
|---|---|---|---|
| **Minimal** | 5–10 条手工冒烟场景 | 无 CI，本地人工跑 | 不采样 |
| **Professional** | 30–100 条 + CI 门禁 | 无回归 + 成本在带宽内（§7 阈值） | 可选轻量采样 |
| **Enterprise** | 100–1000 条 + 生产采样 | §7 阈值 + 趋势告警（成功率/成本斜率异常即告警） | 1%–5% 异步采样 + 失败入 golden set |

**Minimal 手工冒烟示例**：仅覆盖 happy + 少量 edge（如「读一个不存在的文件应报错而非崩溃」），人工核对 `terminal_state`。

## 11. 与本 Skill 其他模块的联动

```
Phase 1–7 构建 ──► 运行时 trace ──┬──► references/14-observability.md 面板（评测结果入面板）
                                  │
                                  ├──► trace 一键导出为评测用例（§8 回流）
                                  │
Phase 4 循环 ──► CONTINUE-SITE-8（验证失败）──► 触发 Phase 8 评测 / 复跑 golden set
```

1. **评测结果进 `references/14-observability.md` 面板**：三层指标（§1）作为 Metrics 支柱的 Agent 专属看板；成功率/成本斜率异常触发该文档的告警规则。
2. **trace 一键导出为评测用例**：生产采样到的失败 trace 可导出为 `evals/scenarios/*.yaml`（自动填充 `assert_trace`/`assert_final`），闭环进 golden set。
3. **与 Phase 4 的 CONTINUE-SITE-8（验证失败）衔接**：当 Agent 核心循环检测到「验证失败」（如自我校验不通过、golden 断言未达），路由到 Phase 8 复跑对应 golden 用例；评测发现的缺口反向进入 CONTINUE-SITE-8 的修复清单。

## 检查清单（按三档分级）

**Minimal**
- [ ] 有 5–10 条手工冒烟场景（happy + 少量 edge）
- [ ] 每条带 `terminal_state` 人工核对项
- [ ] 无整段复制 reference 代码（人工巡检 `anti_copy`）

**Professional**
- [ ] 30–100 条结构化用例（四类矩阵齐全，含 adversarial / off-topic）
- [ ] 全部带 `assert_trace` + `assert_final` 可机检断言
- [ ] judge 一致率 ≥ 85%（含 pairwise 换位测试）后才进 CI
- [ ] CI 门禁启用 §7 默认阈值，安全类 =0 硬门禁
- [ ] `pass^5_happy ≥ 80%`、`pass^1_adversarial = 100%`
- [ ] 成本相对 `baseline.json` 波动 ≤ ±15%

**Enterprise**
- [ ] 100–1000 条用例 + 生产 1%–5% 异步采样
- [ ] 趋势告警（成功率/成本斜率异常）
- [ ] 每次事故永久入库，golden set 年增长 10%–30%
- [ ] 三层指标全量下钻看板（联动 `references/14-observability.md`）

## 常见问题 / 陷阱

1. **用单轮准确率当可靠性**：单输出评分对 §0 四类失败模式全失明；必须评轨迹。
2. **judge 未校准就进门禁**：一致率 <85% 的 judge 会让门禁失效，必须先把关。
3. **忘记 pairwise 换位测试**：不做 swap 约 1/5 的对会沉默投给靠前答案，pairwise 结论不可信。
4. **用 pass@k 代替 pass^k**：pass@k 隐藏方差，可靠性要看 pass^k（k 次全过）。
5. **安全门禁「暂时放松」**：policy_violation / data_leak / budget_breach = 0 是硬门禁，永不放松。
6. **golden set 长期零增长**：说明生产回流失灵，失败模式没沉淀成回归护栏。
7. **anti-copy 只靠肉眼**：必须用 `assert_final.anti_copy.no_verbatim_reference` 做相似度机检，而非人工看。
8. **BLEU/ROUGE 评 Agent 输出**：对 Agent 输出完全无用（答案多样、轨迹为王），不要用。
